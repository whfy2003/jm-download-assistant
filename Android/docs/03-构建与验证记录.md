## 七、第二轮：v1.1 问题修复与回归

真机跑起来后反馈了三个问题，逐个定位如下。

### 7.1 `'AndroidResponse' object has no attribute 'request'`

**根因**：上游 `jm_client_impl.raise_if_resp_should_retry()`（第 1260 行）会读
`resp.request.url`，用来判断 `/chapter_view_template` 特例。`curl_cffi` / `requests`
的 Response 都带 `.request`，我们的适配对象没有。

**修复**：`jmcore/net.py`

* 新增 `_RequestInfo`（method / url / headers / body）；
* `AndroidResponse` 补齐 `request / ok / history / elapsed / reason / encoding`；
* `request()` 在拿到响应后回填 `response.request = _RequestInfo(...)`。

**回归**：`tools/python_smoke_test.py` 增加「响应带 request.url / ok / json」三项，
用假后端直接断言。

**顺带修掉的同类问题：`Set-Cookie` 没解析。**
上游 `ensure_have_cookies()` / `get_cookies()` 读的是 `resp.resp.cookies`，
我们之前固定返回空字典，移动端接口要求携带 cookie，可能因此丢 AVS 或被重定向。
现在：

* `HttpBridge.headersToJson()` 对多值头用换行拼接（之前只取第一条，Set-Cookie 必丢）；
* `net._parse_set_cookie()` 解析成 `{name: value}` 并写入 `response.cookies`；
* 上游随后会通过 `postman['cookies'] = ...` 把 cookie 带进后续请求。

### 7.2 记录列表没有封面缩略图

**方案选择**：不拉网络封面（依赖域名可用性，且对历史记录/收藏/外来 PDF 无效），
改用 Android 自带的 `PdfRenderer` 渲染 PDF 首页。

**实现**：新增 `core/PdfThumbnails.java`

* 后台线程池（2 线程）渲染，`LruCache` 12 MB 做内存缓存；
* 磁盘缓存 `cacheDir/pdf_thumbs/<sha1>.png`，key 含 `lastModified`，文件变了自动失效；
* 渲染前先 `eraseColor(WHITE)`，避免 PDF 透明背景变黑块；
* 列表复用用 `ImageView.tag = 文件名` 校验，防止滚动时图片错位。

### 7.3 深色模式：切换闪烁 + 日志区白底

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 切换时白屏闪一下 | recreate 期间露出旧主题的窗口背景 | 主题加 `android:windowBackground=@color/surface`；切换前先 `window.setBackgroundDrawableResource(目标色)`；`windowAnimationStyle=@null` 去掉重建动画 |
| 运行日志区仍是白底 | 布局里写死 `@color/bg`，没有深色变体 | 新增 `values-night/colors.xml`，同名覆盖 `bg / brand_light / text_secondary / seg_*` 等 |
| 深色下状态栏图标看不清 | `windowLightStatusBar=true` 写死 | `values-night/themes.xml` 覆盖为 `false`（导航栏同理） |

## 八、第三轮：v1.2 修复与新增

### 8.1 WebP 图片下载失败（日志里的 `cannot identify image file`）

**证据**：解包 APK 的 `assets/chaquopy/requirements-arm64-v8a.imy`，Pillow 的原生模块只有
`_imaging.so / _imagingft.so / _imagingmath.so / _imagingmorph.so / _imagingtk.so`，
**没有 `_webp.so`**；而 `requirements-common.imy` 里却有 `PIL/WebPImagePlugin.pyc`。
也就是说「有插件、没解码器」。

**为什么不止是读失败**：上游 `JmImageTool.decode_and_save()` 最终调用
`image.save(path)`，路径后缀来自图片 URL（`.webp`），Pillow 保存同样需要 WebP 编码器。

**修复**：

| 位置 | 内容 |
| --- | --- |
| `core/ImageBridge.java`（新增） | `BitmapFactory` 解码任意格式 → PNG 字节（Android 自带 WebP 解码） |
| `jmcore/imagefix.py`（新增） | 打两个补丁：`open_image()` 失败时走 Android 解码；`save_image()` 遇 `.webp` 改存 `.jpg`（质量 95） |
| `jmcore/task.py` | 下载前 `imagefix.install()`（幂等） |
| `jmcore/api.py` | 环境自检里输出 `image.pillow_webp` 与 `image.imagefix` |

副作用说明：工作区里会得到 `.jpg` 而不是 `.webp`。img2pdf 是按目录遍历文件合并的，
不影响页序；工作区合并后本来就会被清空。

### 8.2 深色模式：页面叠加、再次切换卡死

**根因**：`AppCompatDelegate.setDefaultNightMode()` 会 recreate Activity。
recreate 时 FragmentManager 自动恢复了之前 add 过的三个 Fragment，
但 `MainActivity` 的 `fragments[]` 数组是新建的（全是 null），
`show(0)` 于是又 `add` 一个新的 `DownloadFragment` —— 容器里同时存在多份 Fragment，
看起来就是「设置页和下载页叠在一起」。再次切换时事务继续叠加，最终卡死/黑屏。

**修复**（`MainActivity`）：

* `onCreate` 里 `savedInstanceState != null` 时，用 `findFragmentByTag` 把已恢复的引用接回来；
* `onSaveInstanceState` 保存当前 Tab，recreate 后恢复选中项；
* `show()` 只对「不存在」的 Fragment 调用 `add`，已存在的按 `isAdded/isHidden` 决定 `show/hide`；
* 事务改为 `commitAllowingStateLoss()` + `setReorderingAllowed(true)`，避免重建期抛异常。

**修复**（`SettingsFragment`）：

* 切换加 800ms 防抖；
* 如果 `AppCompatDelegate.getDefaultNightMode()` 已经是目标值，直接返回，不做无意义 recreate；
* `setDefaultNightMode` 放到 `buttonView.post()`，让 Switch 动画先跑完一帧。

### 8.3 新增：下载前预览封面

* `jmcore/api.py` 新增 `preview_album(album_id)`：
  用 `option.build_jm_client()` → `get_album_detail()` 拿标题/作者/页数/章节/标签/简介，
  再用上游的 `JmcomicText.get_album_cover_url()` + `client.get_jm_image()` 下载封面，
  以 base64 返回（复用同一套域名重试与 cookie）。
* `dialog_preview.xml`（新增）+ `DownloadFragment`：
  点「预览封面」弹出对话框，显示封面、标题、作者、页数、章节、标签、简介，
  按钮为「取消 / 开始下载」。
* 下载进行中时「预览封面」按钮同步禁用。

### 8.4 新增：导出运行日志

* `core/LogExporter.java`（新增）：
  Android 10+ 写 `MediaStore.Downloads` → `下载/JM/jm-log-yyyyMMdd-HHmmss.txt`；
  更低版本写到 `getExternalFilesDir("logs")` 并在 Toast 中给出完整路径。
* 下载页状态卡右上角「导出日志」按钮：导出任务编号、状态、消息与最近 200 行日志。

## 九、第四轮：v1.3

### 9.1 下载页「滑不动」

**根因**：`fragment_download.xml` 的根布局是 `LinearLayout`，头部三块（输入卡 ≈150dp、
状态卡含 96dp 日志 ≈200dp、搜索行 ≈60dp、计数 ≈20dp）都是固定高度，
而记录列表靠 `layout_height="0dp" + layout_weight="1"` 占剩余空间。
在多数手机上剩余高度接近 0，列表看不见、自然也滑不动。

**修复**：

* 把「进度条 + 日志」包进 `log_panel`，**默认 `GONE`**；
* 状态行新增「展开日志 / 收起日志」按钮；
* 下载开始时自动展开（`startDownload` 里 `setLogExpanded(true)`），结束后保留用户选择；
* 日志高度 96dp → 110dp（展开时才占空间）。

这样折叠状态下头部约 250dp，列表能拿到 200dp 以上，且可以正常滚动。

### 9.2 代理：账号密码 + 真正生效

**两个问题**：

1. 之前 `proxies` 只传给了 `requests` 后端；而设备上实际用的是 `HttpBridge`
   （`HttpURLConnection`），它根本没读过代理配置 —— 换句话说**代理配了也不生效**。
2. 没有用户名/密码输入项。

**修复**：

| 层 | 内容 |
| --- | --- |
| `jmcore/paths.py` | 新增 `proxy_user` / `proxy_pass`；`snapshot()` 只回传用户名 + `has_proxy_password`，不回传明文密码 |
| `jmcore/net.py` | 新增 `_proxy_config()`，支持 `host:port`、`http://host:port`、`user:pass@host:port`；独立填写的账号密码优先 |
| `core/HttpBridge.java` | 新增 4 个参数的 `fetch` 重载；`Proxy(Type.HTTP, InetSocketAddress)`；HTTP 代理直接带 `Proxy-Authorization: Basic`；HTTPS 走 CONNECT 时用 `Authenticator` 响应 407 |
| 设置页 | 新增「代理用户名 / 代理密码」输入框 + 「测试代理连通性」按钮（先保存再请求 `generate_204`，返回耗时） |

注意：目前只支持 HTTP(S) 代理，SOCKS5 未实现（`_proxy_config()` 会返回 None）。

### 9.3 下载进度与网速

上游 `download_album()` 是阻塞调用，没有可读的实时进度，所以在传输层打点：

* `jmcore/progress.py`（新增）：线程安全的计数器，记录 `done / total / bytes / started`；
* `jmcore/net.py`：`is_image=True` 的响应成功后 `add_image(len(content))`；
* `jmcore/task.py`：开始前用 `client.get_album_detail().page_count` 预取总页数
  （失败只记日志，进度退回不确定态），结束 `finish()`；
* `state()` 增加 `progress` 字段：`{done,total,percent,bytes,speed,elapsed}`；
* `DownloadFragment`：`LinearProgressIndicator` 改确定进度；状态行显示
  `45/120 页 · 3.2 MB/s · 37%`；
* `DownloadService`：通知栏同步百分比进度条与同样的文本。

## 十、第五轮：v1.4（代理认证与进度条收尾）

### 10.1 「代理连通失败」

用户环境：局域网代理 `localhost:8080`，带用户名/密码。

**三层原因**：

1. **传输层不可靠**：v1.3 用 `HttpURLConnection` + `java.net.Authenticator`。
   Android 的这层实现对 HTTPS 的 **CONNECT 隧道 407** 经常拿不到代理凭据，
   表现就是「配了也连不上」；
2. **测试目标不合适**：之前打 `https://www.google.com/generate_204`，
   但这个请求能否成功取决于代理规则/翻墙能力，不是「代理链路是否通」；
3. **错误信息看不见**：只弹一个 toast，无法区分
   「代理没开 allow-lan」「防火墙拦了」「认证失败 407」。

**修复**：

| 位置 | 内容 |
| --- | --- |
| `app/build.gradle.kts` | 引入 `com.squareup.okhttp3:okhttp:3.14.9`（纯 Java，无 Kotlin 依赖） |
| `core/HttpBridge.java` | 整体改用 OkHttp：`proxy(...)` + `proxyAuthenticator`，普通请求与 CONNECT 的 407 都会带 `Proxy-Authorization` 重试；手动重定向、透明 gzip 保持不变 |
| `jmcore/api.py` | `test_proxy()`：默认打 `http://www.baidu.com/generate_204`（只验证代理能转发）；失败时再**直连同一目标**返回对照 |
| `jmcore/net.py` | `request()` 支持 `_no_proxy=True`，供直连对照使用 |
| 设置页 | 测试结果改为**对话框**：代理地址、是否带认证、目标、HTTP 状态、耗时、错误、直连对照，以及排查建议 |

**用户侧仍需确认的三件事**（代码管不到）：
① 代理软件的 **allow-lan / 允许局域网连接** 是否打开；
② 电脑防火墙是否放行 `7893`；
③ 手机与电脑是否在同一网段（`192.168.31.x`）。

### 10.2 下载完成后进度条还在动

**根因**：`applyState()` 的非运行分支把 `LinearProgressIndicator` 设成
`indeterminate=true`；通知栏最终状态也传了 `percent=-1` → `setProgress(..., true)`，
于是两边都会留下一个一直转的进度条。

**修复**：

* 页面：非运行状态先 `setProgressCompat(100/0)`，再 `setVisibility(GONE)`；
* 通知：`percent < 0` 时**不调用** `setProgress`，最终通知没有进度条。

## 十一、第六轮：v1.5

### 11.1 有下载日志，但进度条不动

**根因**（v1.3 埋的坑）：上游 `AbstractJmClient.request_with_retry()` 的签名是

```python
def request_with_retry(self, request, url, domain_index=0, retry_count=0,
                       is_image=False, **kwargs):
    ...
    resp = request(url, **kwargs)     # is_image 被形参吃掉，没有回传给 postman
```

所以我们在 `jmcore/net.request()` 里读 `kwargs['is_image']` **永远是 False**，
`add_image()` 一次都没调用 → `done` 一直是 0 → 页面/通知的百分比不动。

**修复**：

* `jmcore/progress.py` 新增 `install()`：把计数器挂到
  `JmImageResp.transfer_to()`（每张图片保存时走一次，且只走一次）；
* `jmcore/net.py` 删掉基于 `is_image` 的统计，避免重复计数；
* `jmcore/task.py` 在下载前 `progress.install()`；
* `api.diagnose()` 返回 `progress.hooked`，设备上可直接确认钩子是否生效。

### 11.2 代理密码保存后「不能查看也不能修改」

**根因**：`saveRuntime()` 成功后调用 `load()`，而 `load()` 里对密码/Cookie 输入框执行了
`setText("")`。用户刚输入完密码、点「测试连通性」，输入框立刻被清空，
看起来就像「密码被锁住了，只能重写」。`onResume()` 也会触发同样的清空。

**修复**：

* `load(boolean resetSecrets)`：只有**首次进入页面**才清空密码/Cookie；
* 保存成功后调用 `load(false)`，保留用户刚输入的内容；
* 密码提示语改为「代理密码已保存（留空＝保持不变，输入新密码可修改）」；
* 用户名提示语补充「清空会一并清除密码」（与 `paths.set_runtime` 的行为一致）。
